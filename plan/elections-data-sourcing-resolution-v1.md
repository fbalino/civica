# Elections Data Sourcing — Resolution v1

Status: proposed, awaiting owner sign-off on two open questions (§7).
Scope: `elections` / `election_results` tables, `/elections` and `/elections/systems` pages, and any future per-country elections surface (e.g. a `/country/[slug]` elections module).

## 1. Current state

**Data volume.** The `elections` table holds 26 rows across 22 distinct jurisdictions (of 253 sovereign-state jurisdictions in `jurisdictions`) as of 2026-07-04. `election_results` holds 57 party/candidate rows. There is no automated sync — every row was inserted once by hand.

**How the 26 rows got there.**
- `scripts/seed-elections.ts` — a one-time hardcoded array (`ELECTION_DATA`) of 11 elections (Germany, Canada, Australia, US, UK, France, India, South Africa, Mexico, Japan, South Korea, Brazil), each with manually transcribed date/type/system/turnout/results. No source citation, no `sources` row reference, no re-run discipline — it is a seed script, not a sync.
- `scripts/backfill-election-results.ts` — a second one-time hardcoded array correcting/adding results for 3 more elections (Romania, Philippines, Singapore), again manually transcribed with inline comments noting corrections (e.g. "DB currently has this as 'presidential' — this was actually a legislative GE").
- Neither script writes to the `sources` table or calls `markSourcesSynced()`. Neither is wired to a cron. Both are effectively closed one-shot patches — the ~22-country ceiling is a direct consequence of "however many elections someone typed in by hand," not a source-coverage limit.

**What the page actually needs** (`src/app/elections/page.tsx`, `src/app/elections/ElectionsClient.tsx`, `src/lib/db/queries.ts:557-605`):
- Upcoming elections: jurisdiction, `electionDate`, `electionType` (rendered as "`{type}` election").
- Recent elections: same, plus `electoralSystem` (free-text label), `turnoutPercent`, and a party/candidate results bar (`partyName`/`candidateName`, `partyColor`, `votesPercent`, `seatsWon`, `isWinner`).
- Page-level stats: total elections tracked, count this year, upcoming count, average turnout — all computed by a raw SQL aggregate over `elections` joined to `jurisdictions` (`page.tsx:37-53`).
- The hero dek already asserts "voter turnout from IDEA and party-colored results from Wikidata and official sources" (`page.tsx:87-90`) — this describes a target architecture, not what is implemented. No IDEA or Wikidata sync for elections exists today. This resolution is in part about making that sentence true.

**Adjacent infrastructure that already exists and is directly reusable:**
- `scripts/sync-ipu-parline.ts` already calls `https://api.data.ipu.org/v1/chambers` and `/elections/{id}` today, but only to populate `legislature_parties.seatCount` for the *current* legislature — it does not write to the `elections` table at all. It already carries the `ipu_parline` `sources` row, the `statements` provenance pattern, and `markSourcesSynced()` discipline (`sync-ipu-parline.ts:361-369`). This is the cleanest integration point for a first elections-calendar pass.
- `src/lib/data/wikidata.ts` exports `sparqlQuery()`, a retrying, rate-limit-aware SPARQL client already used by `src/lib/factbook/officeholders-sync.ts` and `scripts/sync-wikidata-parties.ts`. Reusable verbatim for a new elections SPARQL sync.
- `elections.wikidataQid` already exists as a schema column (`schema.ts:173`) and is currently unpopulated — the table was designed with Wikidata linkage in mind but it was never wired up.
- `sources` table already has rows for `ipu_parline` (CC-BY-NC-SA-4.0) and `wikidata` (CC0); a `parlgov` row exists (`license: "unspecified"`) but no sync script ever targets it — it is a placeholder, not a live integration.
- `src/lib/elections/electoral-systems.ts` + `plan/electoral-systems-implementation-v1.md` already establish the pattern of storing IPU's own snake_case taxonomy terms verbatim on `government_bodies.electoralSystemFamily`/`electoralSubsystem`, with a documented display-label mapping layer — the same "store the source's own vocabulary, don't invent a Civica taxonomy" discipline should extend to `elections.electionType`.

## 2. Candidate source assessment

Every claim below was verified by live API calls or direct fetch of the cited page on 2026-07-04/05, not from training-data memory.

### 2a. IPU Parline (`https://api.data.ipu.org/v1`)

| Dimension | Finding |
|---|---|
| Coverage | `GET /v1/parliaments` reports `meta.total: 193` (all UN member states). `GET /v1/chambers` reports `meta.total: 280` (193 unicameral + ~87 second chambers). Confirmed live 2026-07-05. |
| Chamber type | **Legislative only.** A substring scan of every `chamber_name` across all 280 chambers for "president" returned zero hits — IPU Parline has no presidential-election concept; it is a union of parliaments. |
| Fields (chamber) | `chamber_code`, `chamber_name`, `parliament` (country code), `last_election.value.from` (date), `electoral_system`/`electoral_subsystem` (dated term objects), `statutory_members_number`, **`parliamentary_term`** (term length in years). Verified live: `GET /v1/chambers/AD-LC01` returns `last_election: {"value":{"from":"2023-04-02T00:00:00.000Z"}}` and `parliamentary_term: [{"value":4,...}]`. A 50-chamber sample (`GET /v1/chambers?page[size]=50`) showed `parliamentary_term` populated on 50/50 and `last_election` populated on 48/50. |
| Next/upcoming election field | **Does not exist.** A full scan of all ~180 attribute keys across all 280 chambers for `next`/`upcoming`/`scheduled`/`future`/`due` substrings returned zero matches. IPU records only the most recent past election date. `parliamentary_term` is present alongside it, so `last_election + parliamentary_term` years is a *derivable estimate* of the next due election — not sourced fact, and must be labeled as a Civica-computed estimate, not an IPU-attributed date (early dissolutions, postponements, and term extensions are common and IPU does not flag them prospectively). |
| Election-record fields | `GET /v1/elections/{chamber_code}-E{YYYYMMDD}` returns `election_title`, `chamber`, `election_code`, `election_date`, four boolean flags, and `election_archive_filename_html` (a linked unstructured HTML archive, not machine-readable). **No turnout field on the election record.** Party/seat data comes from a separate `seats_per_parties` array on the same record (already consumed by `sync-ipu-parline.ts` for current composition) — 2,961 total election records exist, all historical. |
| Turnout | Not present in the IPU API schema inspected. |
| License | Embedded verbatim in every API response's `meta.licence.en`: *"This work is licensed under Creative Commons Attribution-NonCommercial-ShareAlike 4.0 International — https://creativecommons.org/licenses/by-nc-sa/4.0/"*. Terms-of-use link: `https://www.ipu.org/terms-use` (this URL 403s to automated fetches; the CC BY-NC-SA 4.0 grant is authoritative from the API's own metadata, already how Civica treats this source per `seed-sources.ts:47-53`). **Non-commercial only** — matches Civica's existing `ipu_parline` source row (`isCommercialUseAllowed: false`). |
| Access mechanism | Public REST/JSON:API, no key required. `robots.txt` disallows crawling except `/v1/documentation/`; no rate-limit headers observed on API responses. `sync-ipu-parline.ts` already self-throttles with a 200-300ms sleep between calls. |
| Update cadence | Continuous (IPU updates chamber records as elections occur); Civica's own sync is currently run manually, not cron-scheduled. |

Sources: `https://api.data.ipu.org/v1/chambers`, `https://api.data.ipu.org/v1/parliaments`, `https://api.data.ipu.org/v1/elections/AD-LC01-E19931212` (live responses, 2026-07-05); `https://creativecommons.org/licenses/by-nc-sa/4.0/`.

### 2b. Wikidata (`https://query.wikidata.org/sparql`)

| Dimension | Finding |
|---|---|
| Coverage | `COUNT(DISTINCT ?country)` across election entities dated since 2015 = **237** (exceeds ~195 UN states because P17 "country" also captures dependent territories like American Samoa, Isle of Man). Total election entities under `wd:Q40231` (election, all subclasses) dated ≥2015 = **21,625** — this includes municipal, works-council, primary, and other non-national elections; not a usable count on its own. |
| Chamber/office type | **Both legislative and presidential** — confirmed via live query returning "2025 Bolivian general election" (Q100717731), "2026 Haitian presidential election," "2026 Swedish general election," etc. |
| Future/scheduled elections | **Yes, modeled as first-class dated items**, not merely inferred from term limits. Live query with `FILTER(?date > NOW())` returned 33 bindings including Republic of Congo (2026-07-31), Zambia (2026-08-13/08-31), Kazakhstan (2026-08-23), Haiti presidential (2026-08-30), Sri Lanka (2026-08-31), Morocco (2026-09-01), Sweden (2026-09-13), Russia (2026-09-20). This is Wikidata's single biggest advantage over IPU Parline for a calendar feature: **it is the only source in this assessment that carries forward-dated national elections as structured, queryable data.** There is no dedicated "next scheduled election" property — future dates simply use the same P585 (point in time) field as past ones. |
| Results/turnout | **Not reliably present at national-election granularity.** Tested against the 2024 US presidential election (Q101110072): P991 ("successful candidate") resolves to the winner and P726 ("candidate") lists the full candidate roster, but no vote-count, vote-share, or seat-total qualifiers were populated on the item itself. Verdict: Wikidata should be treated as an identity/date spine, not a results source. |
| Data-quality caveats | No single canonical "national legislative election" class — election types fragment into dozens of country-specific QIDs (e.g., Q22266213 Argentine legislative election, Q15974864 Spanish general election) alongside generic ones (Q1076105 general election, Q858439 presidential election, Q2618461 legislative election). The generic classes are NOT nationally scoped by themselves — Q1076105 also returned US state-level and Canadian territorial elections in the same result set as national ones, so a P17=sovereign-state filter plus a curated per-country election-class map is required, mirroring the discipline `sync-wikidata-officeholders.ts` already applies for offices. Crowd-sourced coverage is uneven for smaller states; expect missing future dates for many small jurisdictions until they're formally scheduled. |
| License | CC0 (already Civica's `wikidata` source row) — no attribution obligation, full commercial use. |
| Access mechanism | `query.wikidata.org/sparql`, already wrapped by `src/lib/data/wikidata.ts`'s `sparqlQuery()` (retry + backoff on HTTP 429, already in production use). |

Sources: live SPARQL queries against `https://query.wikidata.org/sparql` run 2026-07-04 (query text and QIDs documented in the research trail for this resolution); Wikidata property/class pages `https://www.wikidata.org/wiki/Q40231`, `https://www.wikidata.org/wiki/Q858439`, `https://www.wikidata.org/wiki/Q1076105`.

### 2d. IFES ElectionGuide (`https://www.electionguide.org`)

| Dimension | Finding |
|---|---|
| Coverage | Confirmed **dual coverage** — the homepage shows both "Upcoming Elections" (forward calendar, populated months ahead) and "Recently Held Elections" (historical results back to the database's 1998 creation). This is one of very few sources in this assessment that actively curates a forward-looking global election calendar with both dates *and* results in one place. |
| Access mechanism | Documented at `https://www.electionguide.org/p/access/`: (1) open web browsing, (2) a registered "User Portal" with XLSX exports of "individual election datasets and basic datapoints for all elections held since 2018," (3) a JSON API described as "a subset of the complete dataset shown... within the User Portal." **All three tiers beyond open browsing require submitting a Data Access Request Form and manual approval** ("A member of the ElectionGuide team will be in touch with login information") — this is not self-serve, and there is no guaranteed turnaround time. |
| License | `https://www.electionguide.org/p/use/`, quoted: personal/non-commercial use (research, teaching) is permitted "provided appropriate attribution is made to IFES ElectionGuide"; "changes must be clearly marked; IFES is not responsible for changes made to the data." **Commercial use is not categorically prohibited** — it requires a separate licensing agreement, with named hard-prohibited use cases (surveillance, targeted political-influence campaigns, predictive markets) and case-by-case approval via `electionguide@ifes.org` for other commercial purposes. This is a materially different, more negotiable posture than IDEA's blanket non-commercial clause. |
| Update cadence | Actively maintained (IFES is a standing electoral-assistance NGO; the calendar showed entries months ahead as of the 2026-07-04 fetch). |

Sources: `https://www.electionguide.org/`, `https://www.electionguide.org/p/access/`, `https://www.electionguide.org/p/use/` (fetched 2026-07-04).

### 2f. Peer practice

Our World in Data does not maintain a dedicated global elections-calendar topic page as of this research; its democracy-adjacent charts lean on V-Dem and Freedom House rather than a curated election calendar. Wikipedia's own "List of next general elections" and per-year election categories are maintained by a standing WikiProject and are the closest existing peer artifact to what `/elections` is trying to be, but they are hand-curated, not API-backed — consistent with the finding above that no single API source combines global coverage, forward dates, and results.

## 3. Recommended architecture

No single source covers date + type + results + turnout + presidential + legislative + past + future at a commercial-friendly license. The recommendation is a **field-by-field authoritative-source model**, matching the pattern Civica already uses for Phase F canonical facts (`resolveFact()` / peer-grouping lens architecture) rather than a single monolithic importer.

| Field | Authoritative source | Rationale |
|---|---|---|
| Legislative election **dates** (past) | IPU Parline `last_election` | Already synced infra (`sync-ipu-parline.ts`), 193 countries / 280 chambers, exact dates. |
| Legislative election **estimated next date** | Derived: IPU `last_election` + `parliamentary_term` years | Not an IPU-asserted fact — must render as a Civica-computed estimate (e.g. "next election due ~2027," not a firm date), because early dissolutions and term extensions are common and unflagged by IPU. |
| Legislative + presidential election **dates** (past and future, as a cross-check / supplement) | Wikidata SPARQL | Only source confirmed to carry forward-dated national elections as structured data; also the only source with presidential-election coverage without a gated access request. |
| Election **type label** | Store the source's own vocabulary verbatim (IPU chamber type → "legislative"; Wikidata class → "presidential"/"legislative"/"general"), same discipline as `electoral-systems.ts` already applies to `electoralSystemFamily`. No invented Civica taxonomy. |
| Electoral **system label** (existing field) | IPU Parline `electoral_system`/`electoral_subsystem` — already synced onto `government_bodies`, just needs to be copied onto the `elections` row at write time. |
| **Turnout** | Not resolvable in v1 without either (a) IDEA under a non-commercial-only posture, or (b) an approved IFES ElectionGuide API grant. Flagged as an open question — see §7. |
| **Party/candidate results, seats** | IPU Parline `seats_per_parties` (legislative, already partially consumed by `sync-ipu-parline.ts`) where available; Wikidata P991/P726 (winner + candidate roster only, no vote share) as a thinner fallback for presidential races. Full vote-share/seat detail for many countries will remain unavailable at this stage — see coverage estimate in §4. |

**Provenance model.** Every `elections` row must carry which source produced which field, following the existing `statements` table pattern (`subjectTable: "elections"`, `subjectId`, `predicate` per field, `sourceId`, `sourceUrl`, `retrievedAt`, `sourceLicense`) — exactly as `sync-ipu-parline.ts` already writes `statements` rows for `legislature_parties.seats_per_parties`. A single `elections` row can and will have mixed provenance (e.g. `election_date` from IPU, `election_type` confirmed by Wikidata cross-check). Do not add a single `sources.id` foreign key column directly on `elections`/`election_results` — that would force one-source-per-row and contradict the mixed-provenance reality documented above; the `statements` table is the correct place to record per-field provenance, consistent with AGENTS.md's "every data point traces to a source row" invariant.

**SourceDot posture.** `elections`/`election_results` rows sourced from IPU or Wikidata syncs are frozen/quarterly-cadence data by nature (a sync run, not a live feed) — per the existing sitewide rule, they render **amber** (frozen), not green, matching how `academic_curated`/quarterly vintages are already treated elsewhere. The `/elections` list page and any future per-country elections module should render a `<SourceDot source="ipu_parline">` / `<SourceDot source="wikidata">` next to each row or section, matching the pattern already live on `/elections/systems` (`ElectoralSystemsClient.tsx:437`) — today's `/elections` list page has no SourceDot at all, which is itself a provenance gap independent of coverage.

**Derived-estimate labeling.** Any "next election due" value computed from `last_election + parliamentary_term` must be visually distinguished from a source-confirmed date (e.g., "Est. 2027" vs. "Nov 5, 2026") so a reader does not mistake a Civica projection for an IPU-published fact.

**Sync cadence.** Both syncs are quarterly-appropriate, not daily — election dates and legislative composition don't change often, and IPU's own robots.txt / lack of rate-limit headers plus the existing 200-300ms self-throttle in `sync-ipu-parline.ts` argue against tight polling. Recommend running both syncs quarterly, on the same cadence as the existing Civica Index dimension ingests, with `markSourcesSynced()` stamped only on non-empty runs per the existing sanctioned-path rule.

## 4. Realistic coverage estimate

| Metric | Estimate after implementation | Basis |
|---|---|---|
| Jurisdictions with at least one legislative election **date** (past) | ~190 of 253 | IPU Parline `parliaments` total = 193; minus a handful with `last_election` unpopulated (2/50 in the sampled batch, i.e. ~4% gap) → realistic estimate ~185-190. |
| Jurisdictions with an **estimated next legislative election** | ~180-185 | Same base minus chambers missing `parliamentary_term` (0/50 missing in sample, so this is a smaller additional loss than the `last_election` gap) — bounded by the `last_election` coverage above since the derivation needs both fields. |
| Jurisdictions with a **presidential** election date (past or future) | Materially smaller than 190 — bounded by which countries are presidential systems at all (per Civica's own regime-taxonomy data) intersected with Wikidata's per-country QID coverage, which was confirmed uneven. No API-derived global count exists; expect this to require the same per-country curation `sync-wikidata-officeholders.ts` already does for offices, not a one-query fetch. Treat as a phase 2 lift, not a v1 guarantee. |
| Jurisdictions with **party/candidate results** (seats or vote share) | Meaningfully more than today's 22, bounded by IPU's `seats_per_parties` coverage on the *most recent* election per chamber (this is the same data `sync-ipu-parline.ts` already fetches for current composition — the 2,961 total IPU election records suggest most recent-election requests will resolve, but full historical back-series is not implied). Realistic v1 target: **most-recent-election results for the large majority of the ~190 legislatures already reachable for dates**, not multi-election back-history everywhere. |
| Jurisdictions with **turnout** | **0 additional, in v1**, pending the open licensing/access question in §7. Today's 22 rows retain their hand-entered turnout values; no source is cleared for a global turnout sync yet. |
| Full ~250-jurisdiction coverage (every sovereign state + all listed territories/entities in `jurisdictions`) | **Not achievable from any combination of these sources.** IPU Parline is capped at 193 UN members; the remaining ~60 rows in `jurisdictions` (dependent territories, disputed/partially-recognized states, micro-jurisdictions like Vatican City) have no legislature to report to IPU and inconsistent Wikidata modeling. "Every country" should be understood as **every sovereign UN-member state**, with non-UN-member jurisdictions carrying an explicit "no comparable legislature" or "limited coverage" state — the same posture Civica already uses for peer-grouping non-coverage cases (Taiwan, Vatican, Western Sahara) per the 2026-05-02 peer-grouping resolution. |

Net: the owner's "needs them all" directive is achievable for the ~190 UN-member states with elected national legislatures — an 8-9x increase over today's 22 — with presidential coverage and turnout arriving in later phases, not v1.

## 5. Licensing posture

- **IPU Parline (CC-BY-NC-SA-4.0)** — non-commercial only. This already governs Civica's existing legislature-composition data and is treated site-wide as acceptable because Civica is not currently a commercial/paid product; the same posture extends cleanly to election dates/results sourced from the same API. If Civica's business model changes (subscriptions, licensing the dataset, ads), every IPU-sourced field — including the newly added elections data — would need to be revisited, not just the pre-existing legislature data. This is not a new risk introduced by this resolution; it is the existing IPU risk surface growing in proportion to how much IPU data Civica displays.
- **Wikidata (CC0)** — no constraint. Full commercial use, no attribution requirement (though Civica already attributes it as a matter of academic practice, not legal obligation).
- **International IDEA turnout (CC-BY-NC-SA-4.0)** — non-commercial only, same constraint class as IPU. Cannot be the basis for the existing hero-copy claim without either accepting the non-commercial posture site-wide (already the de facto stance, since IPU is already non-commercial-gated) or seeking a direct license from IDEA.
- **IFES ElectionGuide** — not blocked by license text alone, but gated behind a manual Data Access Request approval with no guaranteed turnaround or grant. Cannot be scheduled into an implementation plan until IFES actually grants access; treat as a request to send now, integrate later.
- **ParlGov / V-Dem / ACE / Wikipedia** — none selected as primary sources (see §2e), so their license terms do not bind the recommended v1 architecture. V-Dem's existing `academic_noncommercial` posture is already priced into Civica's Index usage and adds no new obligation if used only as a QA cross-check, not a display source.

**Net licensing posture for this feature**: same shape as most of Civica's existing dataset — a commercially-open identity/date spine (Wikidata) blended with a non-commercial-gated depth layer (IPU) — consistent with how Civica already blends `wikidata` + `ipu_parline` for legislature composition today. No new commercial-use categories are unlocked or newly closed by this resolution.

## 6. Implementation outline

Sized S / M / L for a single agent session each; sequencing matters (each phase's DB writes are additive, not destructive).

1. **[S] Schema: no new tables required.** `elections.wikidataQid` already exists and is unused — start populating it. Add one new nullable column, `elections.dateConfidence` (text: `"confirmed"` | `"estimated"`), so the UI can distinguish an IPU/Wikidata-confirmed date from a `last_election + parliamentary_term` projection without overloading `electionDate` semantics. (Everything else needed — `electoralSystem`, `turnoutPercent`, `registeredVoters`, `totalValidVotes` — already exists on `elections`; `election_results` already has the party/candidate/votes/seats/winner shape the page needs.)
2. **[M] `scripts/sync-elections-ipu.ts`** (new script, sibling to `sync-ipu-parline.ts`, reusing its chamber-fetch loop): for each of the ~280 chambers already resolved to a `jurisdictionId`, upsert an `elections` row keyed on `(jurisdictionId, bodyId, electionDate)` from `last_election`, compute and store the `dateConfidence: "confirmed"` date plus a second synthetic row (or a `nextElectionEstimate` — see open question in §7 on whether estimates get their own row or a column) from `last_election + parliamentary_term`, and copy `electoral_system`/`electoral_subsystem` onto `elections.electoralSystem`. Write `statements` provenance rows exactly like the existing `seats_per_parties` write. Extend to also upsert `election_results` from the same `seats_per_parties` payload the existing sync already fetches (currently discarded after populating `legislature_parties` — same API call, currently under-used).
3. **[M] `scripts/sync-elections-wikidata.ts`** (new script, reusing `sparqlQuery()` from `src/lib/data/wikidata.ts`): query for national-level election entities (legislative + presidential) keyed to a curated per-country QID class map (do not trust generic classes like Q1076105 alone — confirmed to leak sub-national results), covering both past and `FILTER(?date > NOW())` future dates. Upsert `elections` rows with `dateConfidence: "confirmed"`, populate `wikidataQid`, and use this pass specifically to fill the presidential-election gap IPU cannot cover. Mirror the curation discipline `sync-wikidata-officeholders.ts` already applies (per-entity validation, not blind bulk insert).
4. **[S] Query layer**: extend `getUpcomingElections`/`getRecentElectionsWithResults` (`src/lib/db/queries.ts:557-605`) to select the new `dateConfidence` column; no join changes needed otherwise.
5. **[S] UI**: add `<SourceDot source="ipu_parline">`/`<SourceDot source="wikidata">` to `ElectionsClient.tsx`'s upcoming and recent election cards (currently absent — a provenance gap independent of this resolution but should ship alongside it), and render `dateConfidence === "estimated"` dates with an "Est." prefix or muted styling per §3's derived-estimate labeling requirement.

## 7. Open questions (genuine owner decisions)

**Q1 — Turnout data: accept IDEA's non-commercial constraint, or hold for IFES ElectionGuide access approval?**
IDEA is usable today but locks turnout data behind a non-commercial posture (consistent with IPU, which Civica already accepts). IFES ElectionGuide has a friendlier commercial path but requires submitting a Data Access Request with no guaranteed grant or timeline. This is a genuine tradeoff between "ship turnout now under a known constraint" vs. "wait on an external approval for a potentially more flexible future." Recommend: send the IFES request now (zero cost, unknown lead time) while shipping IDEA-sourced turnout under the existing non-commercial posture in the interim, then swap/supplement if IFES grants access — but this is a licensing-strategy call, not an engineering one, and should be confirmed before either sync ships.

**Q2 — Does a Civica-computed "estimated next election" date belong on the public page at all, or only source-confirmed dates?**
IPU does not publish future dates; Wikidata does but only where the item has already been created (typically once an election is formally called, which can be close to the date itself, not years ahead). A `last_election + parliamentary_term` projection would materially increase "upcoming elections" coverage but is a Civica-derived estimate, not a cited fact — it sits closer to a forecast than the rest of the site's sourced-fact posture. Recommend confirming whether this crosses the line the 2026-05-02 "research lab" memory-decision draws around asserting novel Civica-derived claims (which would argue for a BETA-style disclosure or a distinctly different visual treatment, per §3's labeling requirement) versus simply excluding estimated dates from v1 and showing "upcoming" only where a source has confirmed a date.
